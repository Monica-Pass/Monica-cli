# Database-first redesign

Current milestone, 2026-09-28: the CLI now has explicit command targets and execution contracts, compact machine discovery, fixed recovery hints and an updated teaching site. MDBX adapters preserve unknown fields and precise JSON numbers; unknown/future objects are read-only, with a human-only masked inspector. Managed copies and WebDAV segments preserve encrypted external Blobs. A numeric precision defect in the packaged Android FFI was fixed in both main and F-Droid runtime sources.

Validation for this milestone: 301 normal CLI tests passed, with independent Android return verification run separately; formatting, all-target Clippy with warnings denied, the release build and generated documentation checks passed. Main Android and F-Droid each passed 210 selected JVM tests and 5 actual application device tests. See [the complete validation record](mdbx-validation-2026-09-28.md) for runtime provenance, scope and limitations. The dated counts below describe earlier milestones.

The core local management and scoped AI gateway workflow is implemented. Remaining release-readiness work includes current-version macOS/Linux acceptance, actual AI-client integration checks, sustained real-cloud/device sync validation, automated core CI gates and audit-log retention. A source push does not publish new downloadable CLI binaries. This milestone does not certify all historical Android adapters or constitute a third-party security audit.

Implemented and tested:

- Launch aliases: `monica`, `monicapass`, `monica-pass` through the Windows installer.
- Default database/category/entry home; nested categories, tree navigation, category rename, entry/category moves. `F3` opens the explicit settings pages.
- `d` lists current and previous databases; `n` creates another database without overwriting the previous one. Switching verifies its password and discards old grants.
- Token creation targets the selected category. Dedicated masked Token replacement preserves the native entry ID and revokes existing grants before replacing the encrypted payload.
- Shared CLI operations: `databases/db`, `use`, `library/tree`, `category/mkdir`, `rename-category`, `move/mv`, `connect --category`, `token`.
- The collection Monica for Android saves new entries into (`nameUUIDFromBytes("monica-root:" + vault id)`, a version-3 id) is seeded when a vault is created and re-created or restored on every unlock, so vaults built by earlier releases become writable on the phone without being rebuilt. Reads never needed the row, which is why such a vault browsed but saved nothing. Deleting or re-parenting it is refused with `protected_collection`; renaming it and filing entries into it stay allowed.
- Without `--json`, `databases`, `library` and `webdav list` print aligned tables with translated headers and the ID each follow-up command needs, and write commands answer with one confirmation line instead of a JSON dump. `--json` envelopes are byte-for-byte unchanged.
- Every AI grant is time-boxed: omitting a duration means the 240-minute default, the configurable range is 1–1440 minutes, and an optional call budget is persisted so a broker restart cannot reset it. Legacy zero windows only survive in older config files. When a window or budget closes, calls return `reauthorization_required` until a person runs `monica refresh <grant>`, which rotates the bearer. Authorization stays revocable and requires an unlocked broker session. The stored credential is permanent until a person replaces it and has no expiry of its own.
- Edit forms separate business fields from the database-password confirmation. Esc from confirmation preserves the draft and clears the password. Every management operation closes its engine session; only summary metadata is cached for up to five minutes. Passwords are not cached to simulate an unlocked vault.
- Settings Token creation remains in settings after saving; the WebDAV/MCP end-to-end test covers this navigation regression.
- EN/ZH quick-start documentation reflects the home/settings split and the bounded AI grant window. The public catalog reports expiry in a separate `authorization` object, so a time box never reads as a credential lifetime.

`monica audit` adds the read side of `gateway.audit.jsonl`, which had been written since the first release but never read by anything in this crate: a trail nobody can open is not a control. It takes `--grant` and `--limit` (1–500, newest first), renders a 6-column table for a person, and keeps `request_id` in `--json` only. The reader projects each line through a 7-field whitelist, so a field a future writer adds cannot reach human or machine output unreviewed; unparsable lines are skipped rather than failing the whole trail. `audit_reader_returns_the_trail_the_gateway_wrote` drives a real `Gateway` (fake upstream, synthetic secrets) and asserts against the file the writer itself produced, including that the token, the vault password and the fixture issue body appear nowhere in it. The table renderer and the command contract are pinned by two further tests. Measured on the real binary: a hand-seeded trail rendered aligned English and zh-CN tables, `--limit 0` and `--limit 501` both exited 2 with the fixed argument-error message, and the reader ran against the developer's own 119-event live trail on a read-only basis. Not measured: the TUI has no audit view, and there is no rotation or retention command — at the 8 MiB cap the broker refuses calls until the operator archives or deletes the file.

The approval gate adds the third budget a grant can carry: a call that needs it does not leave the machine until a person says yes. `ApprovalPolicy::{Off, Write, All}` lives on the grant (`grant --approval`, default `off`, re-set with `grant` or `rf --approval`, and an `Approval gate` field in the TUI grant form), and the check sits in `call_authorized` after every other precondition and after the per-minute charge but before the call budget is spent and before the replay journal row exists — so a refusal leaves nothing to replay and the same `request_id` may be retried unchanged. `src/approval.rs` is process memory only, because only the process holding the unlocked vault can ask: `serve` answers with a `[y/n]` line in its own terminal, the TUI with a modal, and there is deliberately no `monica approve`, no second answering channel and no MCP path back in, since any of those would let the client approve itself. Wait is 15 s, an unanswered prompt lingers 60 s so a late yes is honoured by the retry that follows it, one decision is consumed by exactly one attempt, at most 8 requests are held and the oldest is denied on overflow, and locking the vault or stopping the broker denies whatever is in flight. A broker started without a terminal fails closed and says so at startup if any grant carries a gate. The catalog discloses `authorization.approval` — disclosure only, the policy is never the client's to relax — and `approval_denied` / `approval_timeout` are documented as a person's decision to report, not a fault to route around. Measured on a 0.5.0 release binary against a throwaway vault with synthetic secrets and nothing sent upstream: `approval_timeout` after 15.15 s of wall clock, both grants still at `calls_used: 0`, one `finished / approval_timeout` audit row with no `authorized` row beside it, the `Gate` column in `st`, `"approval":"off"` and `"approval":"write"` in `monica_list_connections`, and the modal read back from a real 120×38 TUI buffer. Not measured: the `serve` `[y/n]` prompt text was never captured through a real pseudo-terminal (`--secrets-stdin` takes the whole stdin and the prompt only exists when stdin is a terminal), and no real LLM client was observed after receiving a refusal. Still open: neither quick-add path (`add`, TUI `a`) can set a gate at issue time, the TUI grant form has no call-budget field, and the prompt does not interrupt an open form or search — such a call waits out its 15 s and is refused.

One-command onboarding removes the paste step. `settings <grant> --install claude|cursor|codex|vscode` still prints and saves the same MCP settings it always did, and additionally merges that one entry into the client's own user-level file: `~/.claude.json` and `~/.cursor/mcp.json` under `mcpServers`, `~/.vscode/mcp.json` under `servers`, `~/.codex/config.toml` under `[mcp_servers.<grant>]` — the four key spellings were confirmed against the files on this machine, and Claude Desktop stays out of the list because its per-platform app-support directory was never verified. `src/install.rs` is the whole feature: it reuses `config::read_json` / `config::write_json` (so the file is written through a private tempfile and a `persist`, with the same oversize ceiling) and `admin::mcp_entry`, lifted out of `mcp_settings` so the printed entry and the written one are the same object — that extraction is byte-identical for its five existing callers. No new crate, so `--offline` is unaffected. The merge is deliberately narrow: other top-level keys and other server entries are untouched, and only the fields this command generates (`command`, `args`) are overlaid onto its own entry, so a block a person added there by hand such as `env` survives a second install; Codex is matched the same way, keeping its `env` sub-table. A file this tool cannot read back in that client's shape — JSON whose top level is not an object, `[[mcp_servers]]`, one grant name defined twice — is refused with `client_config_unusable` and left byte-for-byte alone, and any real change copies the old file aside first as `<file>.monica-<unix>-<seq>`. Re-running is idempotent: no write, no backup, and the note says so. Two accepted side effects are documented rather than hidden: a JSON client file is rewritten with keys in sorted order (serde_json has no `preserve_order`), and a merged file is tightened to owner-read/write. The same commit ships the agent side of onboarding, `docs/agent-policies/AGENTS.md` (self-contained rules to drop into a client's rules file: start from `monica_list_connections`, the hard prohibitions, what an approval gate and each error code mean, how to report back) and its `README.md` (minimal wiring, the client/file/key table, the seven behaviour guarantees, and where to copy the rules). The tool-parameter table is deliberately absent from that file — it would only mirror code and drift; `monica_list_connections` is authoritative — and the README names its drift relationship to `docs/ai-guide.md` §A instead of pretending otherwise.

Two defects found in a review on 2026-09-27 were fixed afterwards, along with an intermittent test failure seen while verifying them.

- A call waiting for a person held the broker's single execution lock for the whole approval window, so every other grant on the same broker got `rate_limited` for up to 15 s — measured on a sandbox broker before the fix. `Gateway::call` is now split into `prepare` (every check that needs no person, under the lock) and `dispatch`; a gated call lets go of the lock while it waits, queues at most 5 s (`RESUME_WAIT`) to take it back once approved, and then re-checks access, the vault lock, the credential and the write journal before spending budget. Three tests pin this, and all three fail on the old code: another grant's discovery and call succeed while a gated call is parked; a grant revoked while the person decided is refused with nothing dispatched and no budget spent (the old path charged the budget first); and a write sent by a twin while the gated copy waited is replayed from the journal rather than sent twice. Concurrent calls on the *same* busy broker outside an approval wait are still serialized and still answer `rate_limited`, as `ai-guide.md` documents.
- `settings --install codex` found an existing entry by scanning for `[mcp_servers.<name>]` lines, so an equivalent spelling (`[mcp_servers.'work']`, `[ mcp_servers.work ]`, an inline table under `[mcp_servers]`, dotted keys) was missed and a second definition appended — reported as success while Codex could no longer parse the file, measured with Python's `tomllib` on four spellings. The merge now parses the file with `toml_edit` (0.22.27; it and its two new transitive crates were already in the local cargo cache, so `--offline` builds still work), edits only `command` and `args` of that one entry, keeps comments and layout, and re-parses the result before writing. Nine spellings are covered by a test that also requires a second run to be byte-identical; the existing byte-level tests pass unchanged.
  A further test writes a Windows command path with a space and an apostrophe (`C:\Users\O'Brien\Apps\Monica CLI`) and requires Codex to read back the exact same string; the release binary did the same against a sandbox `HOME`, checked with `tomllib`.
- Two vault tests failed intermittently (`harmony_login_rows_absorb_and_stay_out_of_the_key_listing`, `the_wider_key_limit_never_opens_a_login_and_the_gateway_never_opens_a_key`). Each captured one timestamp and reused it across several disclosures, while `reveal_key` in between reads the clock itself. The engine treats a timestamp older than the session's last activity as an expired session (`SessionAssurance::is_expired` in mdbx-core), so a second boundary falling between them turned a later disclosure into `UnlockRequired` — confirmed with a throwaway probe that disclosed at `t` and then at `t - 1`. The vault test module now reads the clock at every disclosure through one `now()` helper; product code already did. Test-only change.

The two limits that review left open were closed next, on the same day.

- Calls that arrived while another was running used to bounce with `rate_limited`, an error that told the AI it had been sending too fast when it had only sent two calls at once. The broker still runs one call at a time, but a newcomer now queues for its turn: at most 5 s (`QUEUE_WAIT`) and at most 8 callers (`MAX_QUEUED`), past either of which it gets the new `broker_busy` code with nothing sent and nothing spent. `rate_limited` now means only the per-minute limit, and the AI guide, the agent policy, the human guide and `SECURITY.md` say so.
- A call could outlive the bridge: up to 15 s waiting for a person, up to 5 s queueing to resume, then up to 20 s upstream, against a bridge that stops listening at 25 s. Each call now carries one 22 s budget (`CALL_BUDGET`) from its arrival. The approval wait and the resume queue stop early enough to leave the service 5 s (`UPSTREAM_RESERVE`), the upstream timeout is the smaller of 20 s and what remains, and a call with under 1 s left is refused as `broker_busy` before anything is charged or sent. An unqueued call still gets the full 15 s approval window. Four tests pin this: two calls sent together both succeed; a call queued past 5 s is refused as `broker_busy` and spends nothing; the ninth concurrent caller is refused at once while the queue is full; and a read approved after 8 s against a service that never answers comes back in under 23 s. With the queue wait set to 0 and the budget to 60 s — the old behaviour — the first and the last of these fail, the last after 28 s. The release binary did the same against a sandbox broker whose service base was the unroutable `https://192.0.2.1/`, so every call spent its 5 s connect timeout: two calls sent together both ran, at 5.2 s and 9.8 s; of three, the third came back `broker_busy` at 5.2 s while the other two ran. Every dispatched call left its `authorized` and `finished` audit rows; the refused one left none, as `rate_limited` did before.
- A fresh advisory database (1271 advisories, fetched 2026-09-27) turned up `RUSTSEC-2026-0285` in `rustls 0.23.44`; the lock file now pins 0.23.45. `RUSTSEC-2023-0071` in `rsa 0.9.10` has no fixed release and stays; `SECURITY.md` records why it is judged unreachable here and replaces the stale "no known vulnerabilities" line from 2026-09-12.

Guidance, 2026-09-28: the command line and the practice book both teach the first run better.

- A missing configuration file used to surface as `state_unavailable` ("local state could not be read"), which read like damage on a fresh machine. `ConfigStore::load` now answers `setup_required`, whose message names `monica add <name> --repo <owner/repo>` and `monica next`. `init` and a `status` with no connection or grant end with the same pointer.
- `monica next` reads configuration, grant and broker metadata only — never the vault, a password or an AI client's files — and names the missing step (vault, connection, grant, broker, AI client) with its command; a grant set that has run out is sent to `refresh`, not `grant`. Its `--json` is locale-independent and always spells the binary `monica`; human output uses the name the binary was started under. The last step is advice: nothing here can see whether a client is connected, so it also suggests `check`.
- The root `--help` lists commands in the practice book's seven groups under a three-step quick start and a link to the book. A test requires every visible command to sit in exactly one group and the groups to match `examples.json`. The root summary was never localized (the lookup used the alias `monica-pass`, not the command name `monica`); it is now.
- A mistyped command or flag adds clap's own suggestion, kept only when it names a real command, alias or long flag in the grammar and rewritten from an alias to its command (`grnt` → `grant`, not `g`). The rejected text itself is still never echoed; a test pastes a synthetic token as a command and as a flag value.
- The practice book's default view is now a pixel quest: the drills (13 before, 22 now, at least two per group) sit on a canvas-drawn world map, each with its own win scene, three-step hints and a star rating, followed by the command's captured output. Grading is the same `grammar.js` call as before. The design was sketched first on M3E Canvas (`docs/reference/design-sketch.md`). Measured in headless Chrome on the `file://` page: all 22 levels accept their stored answer, the win scenes render without a script error, a phone-width page has no horizontal scroll, and old `#practice/<id>` links land on the matching level. Not measured: a real phone or a screen reader.

Scope and limitations:

- [Token format](token-format.md) documents the native encrypted API-token payload and Android integration contract. Current Android has a native API-token page; CLI compatibility requires the native type, payload version and schema to match. The cross-client validation above covers precise payload roundtrips and the unknown-object UI, not every Android Token-editor operation.
- Browsing caches public summaries, not an open management session. Saving requires a fresh database password. Cancelling password confirmation preserves the draft; an operation failure after submission currently closes the form.
- The home tree and the connection, grant and WebDAV pages all filter with the same fuzzy subsequence matcher (`/` on the home, a per-page filter elsewhere). It scores only the summaries already on screen, never stored secrets.
- Install only after the application exits; never force-stop a user's session.
